Part B — Deleting the root 40 (two-children case)

Node 40 has two children, so it cannot simply be unlinked. The strategy: replace its data with its in-order successor — the smallest key in its right subtree — then splice the successor's old node out.

Step D1 — Find the in-order successor

From the right child (70), keep going left until a node with no left child is reached:

   70
  /  \
55    85
  \
   60

70 → 55 → (55 has no left child)  ⇒  successor = 55

Step D2 — Copy the successor's data into the root

The root now holds key 55. The original 55 node is still in the right subtree (a temporary duplicate):

    55
   /  \
  20    70
 /  \   /   \
10    30 55  85
           \
            60

Step D3 — Splice the old successor node out

The old 55 has no left child but one right child (60) — the one-child case. Its parent 70 adopts that right child:

70.left = 55.right  ⇒  70.left = 60

Result after deleting 40

    55
   /  \
  20    70
 /  \   /   \
10    30 60  85

In-order traversal: 10, 20, 30, 55, 60, 70, 85 — sorted ✓, size 7 ✓. Node 60 was preserved only because the successor's right child was reattached; forgetting that step would silently lose 60.

Part C — Student-authored unit tests (written before the implementation)

The suite lives in BSTEdgeCaseTest.java and runs on the dependency-free LabTestRunner (no JUnit, pure JDK reflection). Every test documents its input/setup, expected behavior, and the reason the case matters. Tests were authored against TODO stubs first and had to fail; after implementation the same tests must all pass.

TestInput / SetupExpected behaviorWhy this case
testEmptyTree Fresh BinarySearchTree, no inserts. size()==0, isEmpty() true, get(40)==null, delete(40)==null, rangeSearch(10,85) → empty list. Every operation dereferences the root; a naive or stubbed implementation throws NullPointerException here first, so the null-root guards are verified up front.
testRangeSearchInvertedBounds The lab tree built from [40, 20, 70, 10, 30, 55, 85, 60], values "v"<key>. rangeSearch(85, 10) → empty list (not an exception, not garbage). Control: rangeSearch(30,60) → [v30, v40, v55, v60] ascending, inclusive both ends. An inverted [max..min] range is the classic contract bug: stubs and buggy pruning either throw, return everything, or return partial data. The positive control proves the method works, so the empty result for inverted bounds is meaningful.
testDeleteTwoChildrenSuccessorHasRightChild The lab tree; delete(40). Successor is 55 (right child 70, then leftmost) and 55 carries a right child 60. delete returns "v40"; 40 gone; size()==7; get(60) still present; get(55) present exactly once; keys 10/20/30/70/85 intact; in-order keys sorted. This is exactly the Part B trace: copying the successor up without reattaching its right child silently loses node 60 — get(60) is the assertion that catches it.
testPutReplaceKeepsSize The lab tree; put(40, "root") over the existing key 40. put returns the old value "v40"; get(40) yields "root"; size() stays 8. A naive put that always creates a node (or always increments size) silently corrupts the size contract and duplicates keys.
testPutRejectsNullKeyAndValue Empty tree; attempts put(null, "x") and put(1, null). Both throw IllegalArgumentException; size stays 0. A null key would break compareTo during navigation; a null value would make "absent" indistinguishable from "mapped to null".
testDeleteLeaf The lab tree; delete(10) — 10 is a leaf under 20. Returns "v10"; get(10)==null; size()==7; in-order remains [20, 30, 40, 55, 60, 70, 85]. Simplest structural case; catches over-eager child reattachment and size-accounting bugs before the harder delete cases are examined.
testDeleteOneChild The lab tree; delete(55) — 55 has only a right child (60). 55 gone; 60 reattached under 70; size()==7; in-order [10, 20, 30, 40, 60, 70, 85]. Verifies the parent adopts the surviving child — the same splice used when the successor itself is removed in the two-child case.
